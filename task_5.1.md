# Техническое Задание (ТЗ): 5.0 Движок Синхронизации (SyncEngine) - API Сервиса

**Эпик:** 5. 🔄 "Наблюдатель" (Watcher) - Синхронизация, Циклы и Триггеры **Задача:** 5.0, 5.1, 5.1.1 и **5.1.2 (Объединение логики сверки)** **Архитектор:** Gemini **Дата:** 29.10.2025

## 1\. Цель Задачи

Создать **Singleton-сервис** `SyncEngineService`, который выступает в роли **"аудитора"** системы. Его основная задача — **автоматически устранять расхождения** (desync) между внутренним состоянием БД и реальным состоянием на бирже, что критически важно после сбоев, перезапусков или ручных операций.

Эта задача объединяет логику создания API, сверки ордеров-зомби (5.1), судебного восстановления позиций (5.1.1) и обработки исполненных `OPEN_LIMIT` (5.1.2).

## 2\. Архитектурное Решение и Принципы

1.  **Actor-lite (Критично):** Все публичные методы сверки _обязаны_ использовать **`PairActorManagerService`** (Эпик 9). Это гарантирует, что длительная операция сверки _никогда_ не вступит в конфликт с быстрыми операциями `Worker` или `TSLHandler` для той же пары.
2.  **Атомарность (Критично):** Любая операция, которая изменяет БД (удаление ордера, восстановление позиции, конвертация `limit_open` в `ActivePosition`), _обязана_ быть обернута в **`DatabaseService.executeInTransaction()`**.
3.  **Отказоустойчивость:** Сбор всех исходных данных (ордера, позиции, баланс) _обязан_ выполняться **параллельно** с использованием `Promise.allSettled`.
4.  **Точность:** Логика восстановления позиций (5.1.1) _обязана_ использовать **`decimal.js`** для всех кумулятивных финансовых расчетов.

## 4\. Описание и Нюансы Реализации Логики

### 4.1. Метод `reconcileStateForPair(pair: string)`

Это публичный API.

1.  **Враппер (Критично):** Весь метод _обязан_ быть обернут в `await this.pairActorManager.execute(pair, async () => { ... })`.
2.  **Сбор Данных:** Внутри актора _обязан_ выполнить `Promise.allSettled` для параллельной загрузки 4-х ключевых наборов данных: `fetchOpenOrders`, `query(ActiveOrders)`, `query(ActivePositions)`, и **`fetchBalance()`** (для получения баланса базового актива, e.g., BTC).
3.  **Обработка Сбоя:** Если _любой_ запрос провалился (`status === 'rejected'`), _обязан_ залогировать ошибку и **немедленно выйти** (`return`) из актора, не пытаясь выполнить сверку.
4.  **Последовательность Вызова:** При успехе _обязан_ вызвать логику в строгой последовательности (т.к. логика 5.1 может помочь логике 5.1.1):
    - `_reconcileOrders` (Зомби/Призраки).
    - `_reconcilePositionsForensic` (Восстановление).
    - `_reconcileOpenLimitOrders` (Конвертация).

### 4.2. Логика `_reconcileOrders(pair, exchangeOrders, dbOrders)` (Задача 5.1)

Этот метод устраняет ошибки ордеров.

1.  **Сценарий 3 ("Зомби"):** Найти ордера на бирже (SL/TP), которых **нет** в `ActiveOrders` (БД). _обязан_ вызвать `executionService.cancelOrderWithRetry()` для их немедленной отмены.
2.  **Сценарий 4 ("Призраки"):** Найти ордера в БД, которых **нет** на бирже (т.е., исполнились офлайн). _обязан_ **атомарно** (в `executeInTransaction`) удалить их из `ActiveOrders` и `TSL_State`.

### 4.3. Логика `_reconcilePositionsForensic(...)` (Задача 5.1.1)

Этот метод восстанавливает потерянные позиции.

1.  **Условие Запуска (Критично):** Логика _обязана_ запускаться **только** при: `baseAssetBalance.greaterThan(0)` И `dbPositions.length === 0`.
2.  **Транзакция (Критично):** _обязан_ обернуть всю логику в `executeInTransaction()`.
3.  **Восстановление:** Внутри транзакции _обязан_:
    - Сверить `fetchMyTrades` с `TradeHistory` и `INSERT` недостающие записи в `TradeHistory`.
    - Вызвать **`_reconstructPositionFromHistory()`** для расчета `avgEntryPrice` и `totalAmount` на основе обновленной истории.
    - `INSERT` восстановленную позицию в `ActivePositions`. **Критично:** `stop_loss_price` и `take_profit_price` _обязаны_ быть **`NULL`**.

### 4.4. Логика `_reconcileOpenLimitOrders(...)` (Задача 5.1.2)

Этот метод конвертирует исполненные `limit_open` в активные позиции.

1.  **Триггер (Критично):** _обязан_ начать конвертацию, если `dbOrder` с `type === 'limit_open'` **исполнен** на бирже (`status === 'closed'` или ордер исчез).
2.  **Создание SL/TP:** _обязан_ вызвать **`executionService.createOrderWithRetry()`** для создания SL/TP ордеров _на бирже_. _обязан_ делать это **ДО** транзакции БД.
3.  **Шаг 2: Атомарное Обновление (Критично):** _обязан_ обернуть логику обновления в `executeInTransaction()`:
    - `DELETE` старый `limit_open` ордер.
    - `INSERT` новую `ActivePosition`.
    - `INSERT` SL и TP ордера в `ActiveOrders` (используя **реальные ID** с биржи, полученные на Шаге 2).

4.  **Отказоустойчивость:** _обязан_ использовать `try/catch` вокруг создания SL/TP и транзакции. Если транзакция провалилась, _обязан_ залогировать **КРИТИЧЕСКИЙ** сбой, полагаясь на то, что ордера SL/TP будут удалены как "зомби" на следующем цикле (Задача 5.1).

## 5\. Критерии Приемки (Acceptance Criteria)

1.  Service

    `SyncEngineService.ts` корректно принимает _все 7 зависимостей_ через DI.

2.  API(Pair)

    `reconcileStateForPair()` _обязан_ обернуть логику в `PairActorManager.execute()`.

3.  API(DataFetch)

    `reconcileStateForPair()` _обязан_ использовать `Promise.allSettled` для параллельной загрузки 4-х ключевых наборов данных, включая `fetchBalance()`.

4.  Logic5.1

    `_reconcileOrders` _обязан_ использовать `executionService.cancelOrderWithRetry()` для "зомби" и `dbService.executeInTransaction()` для "призраков".

5.  Logic5.1.1(Trigger)

    Логика "судебной" сверки _обязана_ запускаться **только** при условии: `baseAssetBalance.greaterThan(0)` И `dbPositions.length === 0`.

6.  Logic5.1.1(Transaction)

    _Вся_ основная логика "судебной" сверки _обязана_ быть обернута в `this.dbService.executeInTransaction()`.

7.  Helper(Accuracy)

    Логика `_reconstructPositionFromHistory` _обязана_ использовать **`decimal.js`** для всех кумулятивных расчетов и возвращать `null`, если финальный `totalAmount <= 0`.

8.  Logic5.1.2(API)

    `_reconcileOpenLimitOrders` _обязан_ создавать SL/TP ордера через `executionService.createOrderWithRetry()` **до** транзакции БД.

9.  DB(5.1.2)

    _Вся_ логика обновления БД (удаление `limit_open`, вставка `ActivePosition`, вставка `ActiveOrder SL/TP`) _обязана_ быть _атомарно_ обернута в `this.dbService.executeInTransaction()`.

10. Robustness(5.1.2)


    Реализована логика обработки ошибок, которая логгирует `CRITICAL` сбой, но _не_ ломает `SyncEngine`, полагаясь на удаление "зомби" в следующем цикле.
